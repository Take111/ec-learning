# ship — 検証 → コミット → PR作成の一気通貫

このリポジトリで「作業の完成を main に向けて出荷する」ときの手順。
順序は **検証を先、コミットを後**。理由: 壊れた状態をコミット履歴に積まない、
CIで落ちると分かっているものを push しない(CI往復1回 ≒ 数分の節約)。

## 全体の流れ

1. 状況把握とブランチ確認
2. 検証(CIと同じ入口をローカルで先に通す)
3. コミット(commit スキルの規約に従う)
4. push
5. PR作成
6. 結果報告

## 1. 状況把握とブランチ

- `git status` / `git diff` で全変更を把握する(未追跡ファイル含む)
- **main 上にいたら作業ブランチを切る**(main への直接 push はしない)。
  命名は `<フェーズや領域>/<内容>` のケバブケース(例: `phase-d/ci`)
- 既に作業ブランチ上ならそのまま使う

## 2. 検証 — CI と同じ mise タスクを通す

CI(`.github/workflows/ci.yml`)は「操作の入口はすべて mise タスク」の原則で
組んであるので、ローカル検証も同じタスクを呼ぶ。CI の定義が変わったら
こちらではなく ci.yml を正とする。

変更ファイルの範囲で、実行するチェックを選ぶ:

| 変更範囲 | 実行するチェック |
|---|---|
| `api/**` / `db/**` | 下の「API系チェック」を順に全部 |
| `mobile/**` | `mise run mobile-install` → `mise run mobile-check` |
| ドキュメント・`.claude/` のみ | スキップ可(落ちる要素がない) |

**API系チェック**(順序に意味がある — migrate が sqlc 生成の前提DBを作る):

```sh
mise run up          # DB未起動のときだけ
mise run migrate
mise run sqlc && git diff --exit-code -- api/internal/db   # 生成物の乖離検知
cd api && mise exec -- golangci-lint run ./...
mise run api-test    # 実DB統合テスト(並行攻撃・冪等性の実証を含む)
```

- **失敗したら直してから先へ進む**。修正もこれから作るコミットに含める
- 環境要因で実行できないチェック(例: Docker が使えず api-test 不可)は、
  ごまかさず「未実行」として PR 本文の検証欄に理由つきで書く。CI が最終防衛線

## 3. コミット

`.claude/skills/commit/SKILL.md` を読み、その規約に従う。
粒度・メッセージ形式・禁止事項はあちらが唯一の情報源(ここに複製すると乖離する)。

## 4. push

```sh
git push -u origin <ブランチ名>
```

force push はしない(ユーザーが明示的に求めた場合のみ)。

## 5. PR作成

- `gh` CLI が使えれば `gh pr create`、なければ GitHub MCP の
  `create_pull_request`。base は `main`
- **タイトル**: コミットと同じ形式(`<type>: 日本語の要約`)。複数コミットの
  PR なら全体を代表する要約にする
- **本文**: このリポジトリは公開の学習記録なので、PR 本文にも「なぜ」を残す

```markdown
## 概要
(なぜこの変更か。対応するフェーズ・ADR 番号があれば参照)

## 変更内容
- (論理単位ごとの箇条書き)

## 検証
- (何を実行してどう通ったか。例: `mise run api-test` 全パス)
- (スキップしたチェックがあれば理由も)
```

## 6. 結果報告

PR の URL と、ローカルで通した検証のサマリを提示して終わる。

## 注意

- ship を明示的に頼まれたら PR 作成まで確認なしで進めてよい(それがこの
  スキルの目的)。依頼が「コミットして」だけなら PR は作らず commit スキルに従う
- **マージはしない**。レビューとマージはユーザーの仕事
- 既存 PR のブランチで作業していた場合は、新規 PR を作らず push だけで
  既存 PR が更新されることを報告する
