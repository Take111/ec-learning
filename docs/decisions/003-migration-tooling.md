# ADR 003: マイグレーションは連番SQL + 自作スクリプトで運用する

- ステータス: 採用
- 日付: 2026-08-17

## 背景

インデックスを後から張って before/after を比較する学習構成のため、
スキーマ変更が「差分の履歴」として残る仕組みが最初から必要。

## 選択肢

1. **schema.sql 一枚を毎回流し直す** — 差分が履歴に残らず学習記録が消える
2. **golang-migrate 等のツール導入** — 実務標準だが、フェーズAはGoを
   持ち込まない方針。ツールが何をしているか未理解のまま依存が始まる
3. **連番SQL + 自作 migrate.sh** — schema_migrations テーブルで適用済みを
   管理する約30行のシェル。ツールの内部動作を一度自分で書く

## 決定

選択肢3。本体と適用履歴INSERTを同一トランザクション(--single-transaction)で
流す(片方だけ成功→次回二重適用、を仕組みで防ぐ)。マイグレーションファイル
には BEGIN/COMMIT を書かないルール(トランザクションはランナーが所有)。

## 既知の限界(意図的に未対応)

- CREATE INDEX / DROP INDEX の CONCURRENTLY はトランザクション内で実行
  不可のため、この方式では扱えない(ローカル独占環境では不要)
- ロールバック(down)なし。履歴は前に進むだけ。適用済みファイルは
  書き換えず、取り消しも新しい番号で行う(004, 007, 011 が実例)

## この判断が覆る条件

- フェーズDのCI/CD構築時に、この自作経験を判断材料として gomigrate への
  置き換えを再検討する(mise global に導入済み)
